# 記事レビュースキル

記事ドラフトを読み込み、共通の文章ルールとレビュー観点に基づいてフィードバックを行うスキル。レビュー結果をユーザーに提示し、承認後に修正を適用する。

呼び出し例:

```text
/review-article
/review-article articles/2026-04-08-ai-exhibition-behind-the-scenes.md
```

## 前提ファイル

すべてプロジェクトルートからの相対パスで参照する。

- `.claude/shared/writing-rules.md` - 文章ルール、タイトル指針、行動経済学テクニック
- `.claude/skills/review-article/review-checklist.md` - レビュー観点チェックリスト
- `.claude/skills/write-article/article-template.md` / `.claude/skills/interview/article-template.md` - 記事の構成（記事の形に合うほう）
- `.claude/skills/yomiyasu/` - AI が書いた日本語を推敲する yomiyasu スキル（ALGO ARTIS、MIT）

## ワークフロー

### Phase 1: 記事の読み込み

#### 1-1. 対象記事の特定

- 引数に記事のファイルパスがあれば、それを対象にする
- 引数がなければ `articles/*.md` を Glob で検索する
  - 1件だけなら、それを対象にする
  - 複数あれば、更新日の新しい順に最大4件を選択肢にして AskUserQuestion で選んでもらう
- 記事ファイルを Read で読み込む
- `articles/.work/{記事のslug}/material.md` があれば、素材として読み込む（ファクトチェックと yomiyasu の資料に使う）

#### 1-2. レビューの重点

AskUserQuestion で重点を聞く。急ぐ場合は「全体的にレビュー」を選べばよい。

```
question: "特に重点的にレビューしたい観点はありますか？"
options:
  - label: "全体的にレビュー"
    description: "すべての観点でバランスよくレビューする"
  - label: "読みやすさ重視"
    description: "文章の流れ、リズム、AI特有の表現を重点的にチェック"
  - label: "訴求力重視"
    description: "候補者や読者への響き方、魅力の伝わり方を重点的にチェック"
  - label: "正確性重視"
    description: "事実関係、技術用語、表記の正確さを重点的にチェック"
```

### Phase 2: レビュー実行

`.claude/skills/review-article/review-checklist.md` と `.claude/shared/writing-rules.md` を読み込み、以下の観点でレビューを行う。

#### レビュー観点

| カテゴリ | チェック項目 |
|---|---|
| **構成** | 「この記事のポイント」が記事の要約として機能しているか / セクション間の流れが自然か / 素材に引用可能な発言があれば「」引用が活用されているか |
| **文章ルール** | ですます調で統一されているか / 一文100文字以内か / 助詞の連続がないか / 冗長表現がないか |
| **視点の一貫性** | 一人称/三人称が混在していないか / 著者の発言と他者の発言の扱いが正しいか |
| **具体性** | 固有名詞・数値・技術名が適切に使われているか / エピソードが具体的か |
| **訴求力** | タイトルにフックがあるか / 読者が「読みたい」と思える導入か / メッセージが明確か |
| **行動経済学** | アンカリング・社会的証明・損失回避・フレーミング・ピーク・エンドの法則・物語への没入・認知容易性・内集団バイアスが効果的に活用されているか |
| **ファクトチェック** | ツール名・技術仕様・機能名・数値データ等の客観的事実が正しいか（WebSearch で公式情報と照合） |
| **AI文体（yomiyasu）** | 不自然な比喩動詞・擬人化・決まり文句・曖昧な主述関係・過剰な太字や箇条書きが残っていないか（yomiyasu の lint で確認） |
| **textlint** | textlint を実行してエラーがないか |

#### AI文体（yomiyasu）の確認

次のコマンドで見直し候補を出す。採用広報・社内広報は `promo`、テックブログは `article` を指定する。

```bash
python3 .claude/skills/yomiyasu/scripts/yomiyasu_lint.py {記事パス} --doc-type promo
```

候補は合否ではない。元の文脈と照らし合わせ、読みにくさや意味のぼやけにつながるものだけを改善点に含める。

#### ファクトチェックの進め方

記事内の事実主張（ツール名、機能名、仕様、数値、外部サービスの挙動など）を抽出し、WebSearch で公式情報と照合する。

1. 記事を精読し、以下のいずれかに該当する記述を抽出する
   - ツール・プロダクト・サービスの機能説明
   - 技術仕様や挙動の断定
   - 公開されている数値・統計
   - 第三者の製品・サービス名や URL
2. 抽出した記述ごとに WebSearch で公式ドキュメントや信頼できる情報源を検索する
3. 記事の記述と公式情報を比較し、以下のいずれかに分類する
   - ✅ 正確: 公式情報と一致
   - ⚠️ 誤解を招く: 技術的には誤りでないが読者が誤解しうる
   - ❌ 誤り: 公式情報と矛盾する
4. ⚠️・❌ の項目はレビュー結果の「改善点」に含め、根拠となる公式情報 URL を併記する
5. 社内独自の仕組み・数値（「社内で使われている」「時間が X 分」等）は外部検証できないため対象外とし、著者の一次情報として扱う

#### レビュー結果の構造

レビュー結果を以下の形式でまとめる。

```
## レビューサマリー

**総合評価**: {A / B / C}
- A: 公開可能な品質。軽微な修正のみ
- B: 良い内容だが改善の余地あり。修正推奨
- C: 構成や内容に大きな課題あり。書き直し推奨

**良い点**:
- {具体的な良い点を2〜3個}

**改善点**:
- {カテゴリ}: {具体的な指摘と改善案}
- {カテゴリ}: {具体的な指摘と改善案}

**ファクトチェック結果**:
- ✅ 正確: {検証済み項目のリスト}
- ⚠️ 誤解を招く: {該当項目と根拠 URL}
- ❌ 誤り: {該当項目と正しい情報・根拠 URL}

**yomiyasu lint 結果**: 見直し候補 {件数}件（改善点に含めたもの {件数}件）

**textlint 結果**: {エラー数}件
```

### Phase 3: フィードバック提示

レビュー結果をユーザーにテキストで提示し、AskUserQuestion で対応方針を確認する。

`textlint --fix` で機械的に解決できる修正以外は、この確認を完了するまで適用してはいけない。

```
question: "レビュー結果を確認してください。どう対応しますか？"
options:
  - label: "すべて修正する"
    description: "指摘事項をすべて反映する"
  - label: "yomiyasu で推敲する"
    description: "指摘事項を反映したうえで、記事全体を yomiyasu スキルで推敲する"
  - label: "選んで修正する"
    description: "修正する項目を選択する"
  - label: "修正しない"
    description: "現状のままで確定する"
```

### Phase 4: 修正の適用

- `textlint --fix` で解決できる軽微な機械修正は先に適用してよい
- 「すべて修正する」→ ユーザー確認後に、すべての改善点を Edit ツールで適用し、textlint を再実行する
- 「yomiyasu で推敲する」→ すべての改善点を適用したあと、yomiyasu スキルで記事全体を推敲する。文書の種類（`promo` / `article`）と想定読者を伝え、作業ファイルがあれば資料として渡す。推敲した最終稿で元の記事ファイルを上書きしてから textlint を再実行する。yomiyasu の完了報告にある「書き手に確かめたい点」はユーザーに提示する
- 「選んで修正する」→ ユーザーに修正する項目を選んでもらい、選択された項目のみ適用する
- 「修正しない」→ 完了メッセージを表示する

修正後は記事全文を Read ツールで読み込み、ユーザーに提示する。

修正を終えたら、公開用の形式や SNS の告知文が必要なときは `publish-article` スキル（`/publish-article {記事パス}`）で書き出せることを一言案内する。
